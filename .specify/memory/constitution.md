# GEO Insight Constitution

## Core Principles

### I. 口径先行，结果可追溯

指标口径是产品可信度的地基，改动成本高于任何界面工作。

- 所有口径计算 MUST 集中在 `backend/src/geo/domain/metrics.py` 一类纯函数中，
  不得散落在接口层、SQL 片段或前端。输入是样本，输出必须是
  `{value, status, sample_base}` 三件套。
- 口径变更 MUST 同时满足三件事：`metric_version` 递增、经用户确认、跑过黄金样本回归。
  三者缺一，不得合并。
- 样本量低于阈值（默认 3）时，MUST 只返回 `insufficient_samples` 状态，
  MUST NOT 显示 0%、100%、平均排名或涨跌幅。每个指标按自身分母独立判断。
- 页面与报告上的每个数字 MUST 能追溯到样本量、口径版本与统计周期。

**理由**：客户会拿报告质问「为什么是第 6 不是第 3」。口径一旦含糊，
后面所有看板、报告、发布效果对比都不可信，返工成本远高于一开始写清楚。

### II. 未接入必须显式声明

能力边界必须诚实，演示态不得伪装成已上线。

- 任何未真实接入的能力（真实登录、自动发帖、AI 生成、真实采集）MUST 在界面上标注
  「展示态 / 待接入」，并在接口响应中带 `integration: "demo"` 与说明文案。
- 点击 MUST NOT 产生假成功：不得返回伪造的结果、不得扣积分、不得写入「已发布」
  这类与事实不符的状态。
- 可以落库的部分（渠道状态、队列记录）MUST 明确标注为队列/展示数据，不得表述为
  「已发布到某平台」。

**理由**：这类误导一旦进入汇报或对外演示，损失的是信任而不是功能。
用户宁可看到「还没接」，也不愿看到假的已完成。

### III. 律师内容合规红线

产品服务律师业务，内容类功能天然带合规风险。

- 内容生成、编辑与审核环节 MUST NOT 出现对案件结果的承诺性表述
  （如「保证胜诉」「百分百」「包赢」）或不当比较（「最低价」「全网最便宜」）。
- 命中风险词时 MUST 在编辑界面给出提示，并保留下合规记录；提示 SHOULD NOT
  阻断保存，由人决定是否修改。
- 面向客户的报告与文章 MUST 区分「可核实的表述」与「观点」，涉及数字的表述
  MUST 标注来源；无来源的 MUST 标为「待核实」。

**理由**：合规问题不是体验瑕疵，是执业风险。系统不能替律师背书，也不能
在无人注意时生成违规表述。

### IV. 按风险分级的验证

验证强度跟风险走，不搞全量 TDD，也不放水。

- 高风险模块（口径计算、采集解析、计费与配额、数据迁移）MUST 具备：
  来自需求而非实现的断言、**反向验证**（修复前该断言必须失败）、以及相关路径回归。
- 低风险改动（文案、样式、只读展示）MUST 至少做到结构与语法校验，并能说明验了什么。
- 交付汇报 MUST 写明验证到的层级：命令层（能跑）/ 行为层（断言通过）/ 意图层
  （真实路径跑通）。只到命令层就直说「未验证行为」。
- 测试 MUST NOT 写入演示数据库；测试与演示数据 MUST 物理隔离。

**理由**：闸门太严会拖垮迭代，太松会让口径错误溜到客户面前。
分层是唯一能同时成立的解法；而「验证到第几层」能防止用「能跑」冒充「正确」。

### V. 分层与可替换

技术可以换，但换的时候只能动一层。

- 控制器 MUST 只做解析请求、调用服务、格式化响应，MUST NOT 承载业务规则。
- 服务层 MUST NOT 依赖 HTTP 请求/响应对象，便于脱离框架测试。
- 数据访问 MUST 收敛在仓储层；更换存储（SQLite → PostgreSQL / 列式存储）
  MUST 不需要改动口径逻辑与接口契约。
- 引入新依赖或替换基础设施时，MUST 在 `docs/decisions/` 留下决策记录，
  写明代价与触发回退的条件。

**理由**：当前是 SQLite 单进程，将来数据量上来必然要换存储。
只要口径与契约不动，换库就是一次局部替换，而不是重写。

### VI. 先评估，再动手

参考产品是灵感来源，不是施工图纸。

- 接到需求后 MUST 先给出判断：可行性、成本、风险、与现有能力的关系，
  再决定做不做、做多少、先做哪一块。MUST NOT 把「照做」当成交付。
- 截图、视频、竞品 MUST 只作为灵感与形态参考，MUST NOT 默认 1:1 复刻；
  与参考方案不一致时 SHOULD 说明偏离理由与收益。
- 发现方案短板、更优解或与现有架构冲突时 MUST 主动提出，
  并给出推荐选项与各自代价，而不是把问题留到实现完再暴露。
- 需求本身的假设不成立时（例如关键指标拿不到、依赖不可控），
  MUST 先说明这个前提，再讨论替代路径；MUST NOT 用假数据把闭环补齐。
- 无法判断的取舍 MUST 提前问一次；问不清就停，不得先做再解释。

**理由**：复刻一个看得见的界面很便宜，但它会把参考产品的短板一起继承过来，
而我们的优势往往在别处。先评一次，能省掉整轮返工。

## 额外约束：技术形态与数据

- 本宪法**不锁定**具体数据库、部署形态或是否使用容器。相关选择由
  `docs/decisions/` 中的决策记录约束（当前见 `002-local-run-no-docker.md`）。
  形态变更 MUST 留下决策记录，并说明对测试、演示数据与验收步骤的影响。
- 密钥、令牌、真实账号凭据 MUST NOT 出现在代码、示例配置或日志中；
  只允许通过环境变量或本地未入库的配置文件注入。
- 原始答案与引用属于证据材料，任何指标重算 MUST 基于原始记录，不得反向覆盖原文。
- 面向用户的接口错误 MUST 返回结构化 `{code, message, request_id}`，
  MUST NOT 暴露堆栈或内部实现细节。

## 开发工作流与质量门

- 每个特性按 `specify → plan → tasks → implement → converge` 推进；
  产物分别落在 `specs/<feature>/` 下，实现与任务清单必须能互相对上。
- 任务 MUST 带可追溯来源（FR/SC/US 编号）与具体文件路径；无法追溯的工作不进清单。
- 需求存在歧义时 MUST 先问，不得自行假设后直接实现；假设一旦成立，
  MUST 写进 spec 的 Assumptions 或澄清记录。
- 需求进入时 MUST 先产出一次评估（可行性、短板、替代方案、推荐做法），
  再进入 `specify`；评估结论与最终选择 SHOULD 附在 spec 的 Clarifications 或
  `docs/decisions/` 中，便于回溯为什么这么选。
- 每次收敛（converge）MUST 只追加任务、不改写历史任务；缺口按 missing / partial /
  contradicts / unrequested 分类，并给出严重度。
- 演示数据 MUST 可确定性重建（`python backend/run.py --reset`），
  任何人拿到仓库都能得到同一组数字。

## Governance

- 本宪法优先于其它开发实践与个人偏好。与本宪法冲突的实现 MUST 修正或被明确记录为例外，
  例外需要用户确认并写明失效条件。
- 修订流程：提出变更 → 说明影响范围（哪些原则、哪些已实现代码）→ 用户确认 →
  递增版本号 → 同步更新 `Sync Impact Report`。
- 版本策略：MAJOR 为删除或重定义原则；MINOR 为新增原则或实质性扩展；
  PATCH 为措辞澄清与非语义修订。
- 合规审查：每次 `/speckit-converge` 与进入实现前，MUST 对照本宪法检查是否存在
  MUST 违背；违背项按最高严重度处理。
- 运行时开发指引以 `README.md` 与 `docs/decisions/` 为准；二者与宪法冲突时以宪法为准。
