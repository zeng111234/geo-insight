  只有布尔值时这两种 0 引用会混成一个数字，D1 的「2/3 次触发搜索」就没法判。
- 变异自检：把 `search_called = bool(search_blocks) or bool(usage_search)` 改成

## 12:40–13:05 试点 D3：槽位幂等 + 缺口调度 + 采集后自动识别

**发现一个比预期更深的问题**：`row_hash`（含到达秒）与槽位语义冲突。
- 应用层我删掉了 `row_hash_exists` 判重，但**数据库上有 `uq_answer_row_hash` 唯一索引**
  （ON answer(row_hash) WHERE row_hash IS NOT NULL），所以同一天采 3 次、若两次落在同一秒
  且文本相同，仍会被索引拦成"重复"。
- 这不是理论问题：平台对同一问题常逐字返回相同答案，离线库更是必然。
- 修法不是删索引（导入通道靠它去重），而是**让采集的 row_hash 带上日期+槽位**：
  同槽位重试 hash 相同（拦得住），不同槽位 hash 必然不同（3 次采样都能落地）。
  导入通道继续用 collected_at，那边没有槽位概念。
- 变异自检：把 row_hash 改回按到达秒，**7 条测试同时红**——说明这个口径是全局性的。

**槽位设计**：
- `answer.sample_day` + `sample_idx`，唯一索引 `ux_answer_slot`（**部分索引**：
  只约束 sample_day 非 NULL 的行）。历史数据留 NULL 表示"不知道是第几次"，
  不回填——按 id 排序编一个"第几次"等于造一个假维度。
- `max_slot + 1` 而不是 count + 1：中间删过行时 count 会算出已用序号，撞索引。
- 先占槽位再调用：超额检查必须在花钱之前。第 4 次直接 NO_SLOT，一分钱不花。

**缺口驱动才是"同日重跑不重复"的实现**：第一轮采满 → 缺口 0 → 第二轮一条都不采。
不是靠比内容。

**限流收手**：连续 3 次 RATE_LIMITED/TIMEOUT/5xx 结束本轮；配置类错误（NOT_FOUND）
不中止，否则一个写错的问题文本会饿死整轮。变异自检：去掉这段逻辑，
`test_stops_after_repeated_rate_limit` 红。

**增量识别 vs 全量重算的交叉断言**：采集后走 `detect_for_answer`（只算一条），
人工触发走 `recompute`（全量）。两条路径分叉的话，看板提及率会随"什么时候点重算"跳动。
`test_incremental_matches_full_recompute` 直接对拍两者相等。

**CLI 实测**（临时库 + 离线答案库）：3 轮 × 2 秒间隔，目标问题采到 slot 1/2/3、
3 条提及、其他 14 个问题 NOT_FOUND 但不中止。缺口 20 → 17。

验证：单测 384 项全绿（新增 15 条 D3 集成测试），冒烟 106、页面契约、浏览器 DOM、分页全过；
迁移到 v15，演示库 1510 条答案未动；变异自检 3 次（超额检查 / row_hash 口径 / 限流收手）。
