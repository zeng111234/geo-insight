# Feature Specification: 下一阶段演进(真实数据接入与参考系统对齐)

**Feature Branch**: `003-next-stage-roadmap`

**Created**: 2026-11-24

**Status**: Draft

**Input**: User description: "基于 docs/roadmap.md 的演进规划(H2 收尾、H2.5 参考系统对齐、H3 真实平台接入、安全补齐、长久规划),把评估的优先级清单转化为正式 feature spec"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 平台准入调研先行(决策窗口)(Priority: P1)

作为项目唯一维护者,我需要立即启动豆包 / DeepSeek / Kimi 的企业资质、价格、限流、是否允许存储原始回答的调研,因为这项工作不写代码却卡住 H3 全部 10 人日,且资质窗口具有时间敏感性。调研结论直接决定后续路线:有资质走自动采集,没资质把人工采集流程升级为核心流程。

**Why this priority**: 调研不需要代码,今天就能开始,且是唯一卡住"数据真实化"的外部条件。越早拿到结论,越早决定后续约 26 人日往哪走。roadmap 风险登记第一条就是它。

**Independent Test**: 产出一份调研结论文档(每平台含准入条件、价格、限流、存储条款、结论),可用"三个平台每项都有明确结论"来独立验收,不依赖任何其他故事。

**Acceptance Scenarios**:

1. **Given** 我尚未开始任何调研, **When** 我完成三平台调研并写结论文档, **Then** 文档里每个平台的准入条件、价格、限流、原始回答存储条款都有明确结论,且给出"走自动采集 / 走人工流程"的分叉建议。
2. **Given** 某平台需要企业主体 + 对公账户, **When** 调研确认该条件, **Then** 结论文档将该平台标注为"需进一步商业决策",不阻塞其他两个平台的结论。

---

### User Story 2 - H2 收尾(能日常用)(Priority: P1)

作为日常使用者,我需要完成 H2 剩余两项(H2-6 问题集与监控对象绑定、H2-7 引用类型筛选),让"一个人每天靠它干活"的目标闭环。这两项合计 1.0 人日,是全部未完成项里最便宜的。

**Why this priority**: H2 与 H2.5 互不阻塞,1.0 人日即可收尾。H2-7 引用类型筛选同时是 H2.5 E1b(引用栏"全部/已监控"筛选)的口径基础,先做可以避免 E1b 时返工。

**Independent Test**: 按现有验证体系独立验收——H2-6 切换问题集后问题列表与指标口径同步变化;H2-7 筛选后条数与手工统计一致。均不依赖其他故事。

**Acceptance Scenarios**:

1. **Given** 一个监控对象绑定了两个问题集, **When** 我在界面上切换问题集, **Then** 问题列表与所有指标口径同步变化,且黄金窗口断言(22.22%、9 样本)不动。
2. **Given** 引用明细存在 inline/reference/video 三种类型, **When** 我按类型筛选, **Then** 返回条数与手工数据库统计一致。

---

### User Story 3 - 安全补齐:CSRF 防护与登录防护(对外演示前必须)(Priority: P1)

作为系统对外演示的负责人,我需要在任何对外展示之前补上写接口的 CSRF token 校验和登录限流,否则拿到会话 cookie 的任何页面都能静默触发删除、导入、报告生成等写操作,演示期间存在实际风险(README 决策 010 已自认此洞)。

**Why this priority**: 安全洞不是"渐进改善",是"有没有"的问题。`SameSite=None` 加无 token 校验意味着任何第三方页面都能以演示观众的身份发起写请求。且不先补,后面每个新增的写接口(H2.5 E1a 暂停/删除、E3 六阶段、E4 积分)都在扩大攻击面。

**Independent Test**: 用脚本模拟跨站写请求(带 cookie 但无 token)应被 403 拒绝;连续错误登录 5 次应触发限流。均可在服务端独立验证,不依赖页面改动。

**Acceptance Scenarios**:

1. **Given** 已登录会话, **When** 第三方页面携带 cookie 发起写请求但无 CSRF token, **Then** 服务端返回 403,数据不变。
2. **Given** 同一账号连续 5 次密码错误, **When** 第 6 次尝试登录, **Then** 返回限流提示,正确密码在锁定期内也无法登录。
3. **Given** 既有自动化测试(冒烟脚本、页面契约), **When** 引入 CSRF token, **Then** 全量测试数不减且全部通过(测试需先取 token 再请求)。

---

### User Story 4 - 提及识别 v1(数据真实化的第一块拼图)(Priority: P2)

作为数据负责人,我需要系统自动从答案原文识别品牌提及(品牌名+别名精确与归一化匹配),替代当前 seed/导入时手工写 `mentions` 的方式,否则真实采集回来的答案无法产生指标。

**Why this priority**: H3-2 第一个采集适配器跑通后,接下来的问题就是"答案进来了,谁判定提到没提到"。没有它,H3 的采集只是把原文存起来,指标层是空的。

**Independent Test**: 在 30 条人工标注样本上准确率 ≥ 80%,漏检可导出;识别结果可一键清空重跑。不依赖采集器。

**Acceptance Scenarios**:

1. **Given** 30 条人工标注的答案样本, **When** 运行提及识别, **Then** 精确率与召回率 ≥ 80%,漏检清单可导出。
2. **Given** 识别结果已存在, **When** 我修改品牌别名后一键重跑, **Then** 旧结果被清空,新结果按新别名计算。

---

### User Story 5 - H2.5 参考系统对齐(客户观感层)(Priority: P2)

作为对客户演示的人,我需要按决策 009 的顺序完成 E1a~E1e(对象头按钮组、引用第三栏、行内复制、模型×端渠道、筛选条、新建抽屉),让系统看起来"和客户在用的系统是同一个东西"。

**Why this priority**: 15.2 人日里 E1+E2 合计 6.2 人日是性价比最高的一段,顺序是硬约束(E0→E1a/b/c→E2→E1d→E1e→E3→E4)。E2(模型×端 16 渠道)必须早于 E1d(筛选条),否则"模型"筛选维度要改两次。

**Independent Test**: 每个 E 项都有 roadmap 已定义的验收断言(如"导出条数 = 当前筛选样本数"),可逐项独立验收。

**Acceptance Scenarios**:

1. **Given** 问题监控页, **When** 我点对象头"导出 CSV", **Then** 导出条数等于当前筛选样本数,暂停监控后状态落库。
2. **Given** 模型×端的 16 个渠道, **When** 同日同模型不同端有答案, **Then** 分开统计,老数据默认 `web`,13 个空渠道显式"未接入"。
3. **Given** 筛选条(品牌/问题/模型/日期)位于 tab 之上, **When** 切换筛选, **Then** 10 个 tab 数字同步变化,刷新保住筛选状态。

---

### User Story 6 - H3 采集调度与失败处理(真实数据自动化)(Priority: P3)

作为运维者,我需要进程内采集调度器(幂等键防重复)、失败重试与失败率告警,让"真实数据自动进来"不必人工盯守。

**Why this priority**: 依赖 US1 调研结论。有资质时走适配器 + 调度器;无资质时调度器优先级下调,人工流程升级为主流程。排在 P3 是因为外部依赖未决。

**Independent Test**: 重复调度同一 (问题, 模型, 日期, 样本序) 不产生重复样本;失败原因可分类型统计。可用离线采集器验证,不依赖真平台。

**Acceptance Scenarios**:

1. **Given** 调度器已启动, **When** 同一幂等键重复触发, **Then** 只产生一条样本记录。
2. **Given** 失败率阈值已配置, **When** 某模型当日失败率超过阈值, **Then** 呈现告警,失败原因有分类统计(超时/风控/拒答)。

---

### User Story 7 - AI 助手与积分账本(E4,最贵)(Priority: P3)

作为内容运营者,我需要 AI 助手与积分账本,但这是对齐参考系统观感的最贵一段(4.5 人日),建议在有真实数据后再做。

**Why this priority**: E4 依赖 E3(六阶段流水线),且"AI 真调 LLM"需要真实平台成本,与 H3 有耦合。建议排在 H3 验证真实数据价值之后。

**Independent Test**: 余额 = 流水求和;AI 调用真实发起模型请求或显式标失败。

**Acceptance Scenarios**:

1. **Given** 积分账本有充值与消耗流水, **When** 查询余额, **Then** 余额等于全部流水求和。
2. **Given** AI 助手发起分析, **When** 模型服务不可用, **Then** 显式标注失败,不编造结果。

---

### Edge Cases

- 平台准入调研结论为"三个平台都需要企业主体"时,路线分叉为人工流程强化版,本 spec 的 US6/US7 优先级整体下调,H2-2 缺样本清单流程升级为 P1。
- CSRF token 引入后,既有 442 条自动化测试需要同步适配(先取 token 再请求),若某类测试适配成本过高,允许对该类做最小化适配而不是逐条重写。
- 提及识别在"否定句提及"(如"不建议选 A 品牌")上的表现需单独标注:该类样本应按"提及但负面情感"处理,不是"未提及"。
- H2-6 切换问题集时,若两个问题集的核心词不同,核心词判定与跑题判定需同步切换,不能沿用旧集的核心词。
- 维度重叠:E1b 引用栏筛选与 H2-7 引用类型筛选共用口径,实现时必须同一份过滤逻辑,不允许两处各写一套。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在平台准入调研完成前不启动任何真实平台采集的代码工作;调研结论以文档形式归档,三个平台每项条件都有明确结论。
- **FR-002**: 系统 MUST 支持"平台准入失败"的降级路线:人工采集 + 缺样本清单 + 导入的闭环流程升级为核心流程,并补齐该流程的日常使用文档。
- **FR-003**: 监控对象 MUST 支持绑定多个问题集并切换;切换后问题列表、指标口径、核心词与跑题判定同步变化。
- **FR-004**: 引用明细 MUST 支持按类型(inline/reference/video)筛选,筛选结果与直接数据库统计一致。
- **FR-005**: 所有写接口 MUST 校验 CSRF token(一次性 token 或双提交 cookie),无 token 或 token 无效返回 403,数据不变。
- **FR-006**: 登录接口 MUST 支持限流,连续错误超过阈值后,锁定期内即使密码正确也拒绝登录。
- **FR-007**: 提及识别 MUST 支持品牌名与别名的精确匹配和归一化匹配(大小写、全半角、常见错写),识别结果支持一键清空重跑。
- **FR-008**: 提及识别 MUST 在 30 条人工标注样本上精确率与召回率 ≥ 80%,漏检清单可导出。
- **FR-009**: 监控对象头 MUST 提供导出 CSV / 下载报告 / 暂停监控 / 删除四个操作;导出条数等于当前筛选样本数;暂停与删除落库并写审计。
- **FR-010**: 采集执行 MUST 记录失败原因分类(超时/风控/验证码/拒答),失败率超过阈值时呈现告警。
- **FR-011**: 原始响应存档路径 MUST 用可区分的前缀(如 `collect://`)把真实数据与演示数据(现有 `s3://geo-raw/demo/`)分开,报告与页面有可见标识。
- **FR-012**: 每个阶段收尾 MUST 满足 roadmap 第七节的硬约束:全量自动化测试数只增不减、黄金窗口手算值不动、结构变更只走新增迁移版本。

### Key Entities

- **调研结论(平台准入)**: 每平台记录准入条件、价格、限流、原始回答存储条款、结论与分叉建议;归档为文档,是路线决策的唯一依据。
- **监控对象-问题集绑定**: 一个监控对象与多个问题集的关系及当前生效集;切换影响问题列表、指标口径、核心词与跑题判定。
- **CSRF 凭证**: 登录会话关联的防伪凭证,写接口校验,与会话同生命周期。
- **提及识别任务**: 对一批评案执行品牌/别名匹配的任务,含识别结果、人工标注基准、重跑语义(清空后重算)。
- **采集渠道(模型×端)**: 采集执行的最小通道维度,同模型不同端分开统计;含 13 个未接入渠道的显式标注。
- **采集调度幂等键**: (问题, 模型, 日期, 样本序) 组合,保证重复调度不产生重复样本。
- **失败分类记录**: 采集失败的原因归类(超时/风控/验证码/拒答)与按日失败率,超过阈值触发告警。
- **积分流水**: 账本条目(充值/消耗/退款),余额恒等于流水求和。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 平台准入调研在 1 周内完成结论文档,三平台每项条件有明确结论,路线分叉决策有据可依。
- **SC-002**: H2 收尾后,连续 3 天按"缺样本清单导出 → 人工采集 → 导入 → 指标更新"流程操作,全程不需要直接接触数据库。
- **SC-003**: 引入 CSRF 防护后,模拟跨站写请求 100% 被拒绝(403),且既有全量自动化测试数不减、全部通过。
- **SC-004**: 提及识别在 30 条人工标注样本上精确率与召回率均 ≥ 80%。
- **SC-005**: H2.5 的 E1+E2 完成后,问题监控页具备对象头四操作、引用第三栏、行内复制、16 渠道与筛选条,刷新后筛选状态保持。
- **SC-006**: 真实数据进入后,任何报告与页面都能一眼区分真实数据与演示数据。
- **SC-007**: 每个阶段收尾时,全量自动化测试数不低于 442,黄金窗口 19 项手算值(含 22.22%、9 样本)不变。

## Assumptions

- 目标仍是单用户单租户的演示演进,H4(多用户/多租户/PostgreSQL)与 H5(计费/SLA)不在本 spec 范围,只作为长久规划背景。
- "人工采集 + 导入"闭环已存在且被验证过(roadmap H2-2),本 spec 只在其上增强,不重建。
- CSRF 方案沿用现有零依赖原则:优先一次性 token 或双提交 cookie,不引入大型安全框架。
- 平台调研以豆包 / DeepSeek / Kimi 三个国内平台为首批对象,海外平台(GPT/Gemini)后置。
- 黄金窗口演示数据与 442 条测试体系作为回归基线持续有效,任何改动不得使其衰减。
