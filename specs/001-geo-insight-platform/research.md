# Phase 0 研究：GEO Insight 首版

**Feature**: `001-geo-insight-platform`
**Date**: 2026-11-11
**输入**: `spec.md`、`docs/GEO-Insight-整体方案.md`、`docs/decisions/001-clarifications.md`

本文件只记录「决定 + 理由 + 放弃的方案」，不写实现代码。所有决定都能回指到 spec 的 FR/SC。

---

## R-01 采集通道：首版不实施，架构保留双通道

**Decision**: 首版不接入任何真实采集。数据模型与接口保留 `channel` 维度（`api` / `web`），指标计算按通道隔离，不允许跨通道合并。

**Rationale**: 澄清记录 C-02 明确当前阶段只出方案。保留 channel 的成本很低（一个枚举 + 一个过滤维度），但后期补上的改造成本很高（指标宽表要重算、报告要重出）。先把位置留出来。

**Alternatives considered**:
- 首版就做网页端采集：登录态、验证码、DOM 稳定性都未验证，会把工期赌在不可控因素上。
- 完全去掉 channel：以后补采集时，历史指标无法区分来源，等于全部作废。

## R-02 列表序号识别：规则优先，模型兜底

**Decision**: 按以下顺序判定位次：
1. 解析答案中的有序列表（Markdown `1.`、HTML `<ol>/<li>`、纯文本「1、」「（1）」编号行、表格行）。
2. 品牌首次出现在某个列表项内 → 取该项序号。
3. 规则无法判定但文本疑似列表（如「推荐如下：A…B…C…」）→ 交给模型判断，输出 `{index, confidence}`。
4. `confidence < 0.7` 或没有列表 → `position = null`，归入「无列表样本」。

**Rationale**: 纯规则能覆盖大多数结构化答案，成本低、可复现；纯模型判定不可复现、成本高、难以解释。规则 + 低置信兜底，兼顾准确率与可审计性。

**Alternatives considered**:
- 纯 LLM 判定：每条答案都要调用，成本高，且同一答案两次调用可能给不同序号。
- 纯字符位置：已澄清否决（C-01）。

**风险**: 中文答案的「1、」「一、」「第一」格式混杂，规则需要持续补样本；黄金样本集要覆盖这些格式。

## R-03 品牌提及检测：词典 + 归一化 + 模糊召回

**Decision**: 三路合并：
1. 精确匹配：品牌全称、别名、英文名、常见错写。
2. 归一化匹配：全半角、大小写、空格、标点差异。
3. 模糊召回：编辑距离 ≤ 1 或向量相似度 ≥ 0.9，且必须通过「不是其他已知品牌」的排除。

命中后统一记录 `matched_alias` 与 `match_type`，便于人工复核。

**Rationale**: 中文品牌简称多、错写多，纯精确匹配会漏；纯模糊匹配会把竞品误判成本品牌。三路合并 + 排除规则，误判可控。

**Alternatives considered**:
- 只用 LLM 抽取实体：成本高，且对同音错写不稳定。
- 只做精确匹配：召回率不够，客户会立刻发现「明明提到了但没算」。

## R-04 情感判定：片段级三分类，平票保守

**Decision**: 以「品牌相关片段」为单位调用模型做三分类（正/中/负），规则词典作为兜底与一致性校验。同一答案多个片段不一致时按数量取多数；平票按「负面 > 中性 > 正面」取值。未提及品牌的答案**不进入情感分母**。

**Rationale**: 整篇答案的情感无法归属到品牌；把未提及算作「中性」会制造「0 提及、100% 中性」的假象（截图里就出现过这种显示）。分母必须是提及样本。

**Alternatives considered**:
- 整篇答案情感：无法归属，多品牌场景尤其错误。
- 全部样本作分母：会把「没提到」算成中性，扭曲指标。

---

## R-05 存储分工：PostgreSQL 业务 + ClickHouse 明细

**Decision**:
- PostgreSQL 16：租户、品牌、问题、监控、任务、报告元数据、审计。带 `tenant_id`，启用行级安全（RLS）。
- ClickHouse：`answer_fact`、`citation_fact`、`metric_daily` 三张宽表，按 `tenant_id + tracker_id + date` 分区。
- 两库不做分布式事务：PG 写业务事实并落 outbox，异步投递到 CH；CH 侧按 `answer_id` 幂等写入。

**Rationale**: 业务表要事务与约束；答案/引用是日志型宽表，聚合量大。用 PG 硬扛会让看板随数据量线性变慢；用 CH 做业务库会失去更新与事务能力。

**Alternatives considered**:
- 单 PG + 分区表：首版数据量能撑，但 6 个月后指标查询会明显退化。
- 单 CH：无法支撑配置类业务的事务与唯一约束。

**风险**: 双写一致性靠 outbox + 幂等消费，必须监控延迟；对账任务每天跑一次。

## R-06 指标预聚合与口径版本

**Decision**: 每小时增量聚合一版日粒度宽表 `metric_daily`，字段包含 `metric_version`、`sample_total`、`valid_total`、`mention_total`、`ranked_total`、`top1/3/10`、`sentiment_pos/neu/neg`。所有页面只查宽表；下钻才查明细。

**Rationale**: 看板 P95 < 2s 是硬指标（SC-002），实时扫答案不可能达标。口径版本让「定义变更后重算」成为可能。

**Alternatives considered**:
- 查询时实时聚合：答案量到十万级就会超时。
- 物化视图自动刷新：CH 物化视图对迟到数据不友好，改为可重跑的批任务更可控。

---

## R-07 报告快照与导出

**Decision**: 报告生成时把指标、图表数据、结论、样本量、口径版本写成一个不可变 JSON 快照；页面渲染与 PDF 导出都读这份快照。PDF 用 HTML 模板渲染后转 PDF。

**Rationale**: FR-028 要求 30 天后打开数字不变。如果报告每次实时查库，口径或数据一变就不可复现，客户会认为报告「会变」。

**Alternatives considered**:
- 实时报告：不可复现，不能作为交付物。
- 只存截图：无法检索、无法改版式、无法做无障碍。

---

## R-08 调度与失败处理：Celery + 幂等键

**Decision**: Celery + Redis 做任务队列与定时调度。`run_item` 唯一键 `(run_id, question_id, model_id, channel, sample_idx)`；失败重试 2 次，指数退避；失败不计入有效样本与分母。

**Rationale**: 首版任务形态简单（批量采样、聚合、报告），Celery 足够且运维成本低。长流程（内容审批、发布）不在首版，暂不需要 Temporal。

**Alternatives considered**:
- Temporal：能力强，但首版引入额外集群与学习成本。
- 纯 cron 脚本：没有重试、可视性与并发控制。

---

## R-09 多租户与权限：字段先行，RLS 落地

**Decision**: 所有业务表带 `tenant_id`；首版只开放单团队使用，不做租户注册与计费；但 RLS 策略与角色（admin/operator/viewer）从第一版就建好。

**Rationale**: 澄清与 spec 的首版范围是单团队内测，但后续要做代理商模式。字段与策略先建，避免以后改表；不开放注册则不增加首版交互复杂度。

**Alternatives considered**:
- 首版完全不做 tenant_id：后续迁移要改所有表与查询，风险高。
- 首版就做完整多租户：超出首版范围，拖慢交付。

---

## R-10 测试策略：黄金样本集 + 契约测试

**Decision**:
- 指标正确性：200 条人工标注的黄金样本集（覆盖有列表/无列表/否定句/多品牌/错写别名），作为回归基线。
- 契约：OpenAPI 用 Schemathesis 做属性测试，保证实现不偏离 `contracts/openapi.yaml`。
- 前端：Playwright 覆盖 P1 的 4 条验收场景。

**Rationale**: SC-003 要求提及一致率 ≥ 90%、情感 ≥ 85%，没有固定样本集就无法证明。契约测试能防止前后端各自解释字段。

**Alternatives considered**:
- 只写单元测试：无法覆盖「答案 → 指标」的端到端口径。
- 只做人工验收：不可重复，回归成本高。
