# 效果试点计划（2026-11-25）

> 目标不是"页面像参考系统"，是**客户的品牌在 AI 答案里真的变好，而且能证明**。
> 这份计划只覆盖到"第一个可信的效果结论"；复刻、16 渠道、积分都排在它后面。
> 时间口径：1 人日 = 8 小时；按每天 1 个有效人日排。你若一天能推 2–3 人日，代码段可压缩，观察期压不了。
>
> **先看清"10 天"是什么**：下面的 D1–D10 是**试点代码段**（10 个工作日 ≈ 2 个日历周），不是整个项目。
> 完整时间线：第一个效果结论约 **5 周**（2 周代码 + 3–4 周观察）；规模化约 **7–8 周**；加完整复刻约 **9 周**。见第七节。
> 如果按 AI 节奏推进（2–3 人日/天），见第八节：**5 个工作日把采集/归因跑通，第 8 天发文章，第一份结论约 3 周**。
>
> **接入方式已核实（2026-11-25）**：DeepSeek 与豆包的官方 API 都支持联网搜索并返回引用（见第一节的表）。
> 本计划走 **API 自动化**，人工采样只在 API 触发不了搜索、或核对产品端差异时做兜底。

## 一、试点定义

**1 个问题 × 1 个平台 × 1 篇文章 × 1 个渠道 × 至少 14 天（最好 30 天）。**

### 三个角色别混

- **被测平台（DeepSeek / 豆包 / Kimi）**：我们向它提问，看答案里有没有客户品牌、排第几、引用了谁。它是"体检仪器"，**不是发文章的工具**。
- **发布渠道（知乎 / 公众号 / 搜狐）**：文章发到这里，用现有的 publisher CLI；这一步和 DeepSeek 无关。
- **内容**：人写，或用 LLM 辅助；系统里的采集器只负责"问 + 收答案"，不负责写稿。

- 平台：**DeepSeek 和豆包都已有官方联网 API，且都返回引用**（2026-11-25 核对官方文档）：

| 平台 | 联网方式 | 引用字段 | 计费 | 结论 |
|---|---|---|---|---|
| DeepSeek | `deepseek-flash` + `deepseek_web_search` | Messages `citations[]`；Chat/Responses `annotations[]` | 服务端搜索不计费，只算 token（约 ¥100/月） | 成本最低、字段最全；**只做一件事就选它** |
| 豆包/火山方舟 | Chat API `web_search_options`，或 Responses `tools:[{"type":"web_search"}]` | `annotations` 的 `url_citation`（url/title/site_name/publish_time） | 搜索按次计费 | 用户量大、答案级引用；**客户人群主要在豆包就选它** |
| Kimi | Responses `tools:[{"type":"web_search"}]` | `web_search_call.action.sources` | $0.005/次 + 模型较贵 | 备选 |
| 千问 | DashScope 原生协议 | `search_info`（检索面，非答案级） | — | 暂不用 |

  D1 用同一个问题各跑 DeepSeek / 豆包 3 次，比较「是否触发搜索、引用条数、是否提到品牌」，选一个主平台，另一个做交叉验证。
  **不要用人工采样做主路径**；人工只在 API 触发不了搜索、或要核对产品端差异时做兜底。
  > 来源（2026-11-25 访问，均为官方域名）：DeepSeek `https://api-docs.deepseek.com/zh-cn/guides/web_tools/`；
  > 火山方舟 `https://www.volcengine.com/docs/82379/1756990`；Kimi `https://platform.kimi.ai/docs/api/responses`。
- 问题：目标问题 1 个 + 对照问题 1 个（同类、但本次不投放）
- 渠道：知乎 / 公众号 / 搜狐 中选一个已登录、能发文的
- 样本：目标与对照各 3 次/天；发布前至少 5 天基线，发布后观察 14–30 天

### 判定规则（发布前写死，不许事后挑数据）

| 指标 | 通过线 | 说明 |
|---|---|---|
| 主指标：目标问题提及率 | 发布后 14 天比发布前 7 天提升 **≥ 20pp**（基线 0 时约等于 21 条样本里出现 5 条提及），且提及样本 ≥ 3 条 | 样本 ≥ 21 条/窗口；不足标"样本不足" |
| 对照：同期未投放问题 | 变化 **< 10pp** | 排除"大盘都在涨" |
| 次指标：平均位次 / 情感 | 位次改善或进入前 3；情感不为负 | 有位次的样本才算 |
| 引用归因（可选） | 发布文章 URL 在答案引用中出现 ≥ 1 次 | 平台不返回引用时标"不可测"，不硬凑 |

不满足主指标 → 结论写"**未证明**"，不是"失败"；先分析内容/渠道/平台，再决定是否迭代一次。

## 二、10 个工作日（D1–D10）

| 天 | 交付 | 判据 |
|---|---|---|
| **D1** | 平台对比：同一问题各跑 DeepSeek / 豆包 3 次，记录是否触发搜索、引用条数、是否提到品牌；选定主平台；建试点 tracker + 目标/对照问题 + 采样计划（3 次/天） | 两家都能返回引用；选出主平台并说明理由；真实回答入库，`raw_uri=collect://...`；记录延迟、费用、搜索触发率。**目标问题至少 2/3 次触发搜索，否则换问法或加「请联网查」提示（标记为搜索增强模式）** |
| **D2** | 采集 adapter 完成：错误分类（401/429/5xx/超时/空回答）、原始响应落盘、token/cost、**`search_called` / 搜索次数 / `citations`（url/title/site_name/publish_time）解析并写入 `citation` 表**；CLI `--once` | 四类失败都能归类；一次成功调用字段完整；「没搜索」与「搜了没引用」能分开统计；单测用假 HTTP，不花真钱 **→ 代码已完成 2026-11-25，真调用待 key** |
| **D3** | 调度 + 幂等：进程内循环，幂等键（问题, 模型, 日期, 样本序）；采集后自动跑提及识别 | 同日重跑不产生重复样本；缺口清单归零；提及数与手工核对一致 **→ 代码已完成 2026-11-25（离线库验证），真调用待 key** |
| **D4** | 归因 v1：`/articles/{id}/impact` 按 `question_id` 限定 + 按模型拆 + 7/14/30 天窗口；URL 归一化匹配（引用解析已就绪） | 与手工 SQL 对拍；对照问题不受影响；http/https、尾斜杠、utm 变体测试通过 |
| **D5** | 渠道连接 + 1 篇文章：登录/检测；选择器校准（首跑 `--show`）；文章围绕目标问题写（品牌、事实、来源、小标题） | 渠道 `connected`；草稿在平台后台可见；标题/正文过平台规则 |
| **D6** | 真实发布 + 实验记录：`published_url`、发布时间、目标问题、渠道、基线窗口 | `publication.status=published`；URL 可访问；基线 ≥ 5 天 × 3 次 |
| **D7** | 试点看板（目标 vs 对照、日提及率、样本数、发布日标线）+ 数据库备份/恢复 | 看板与接口一致；恢复后单测全绿 |
| **D8** | 缓冲：处理限流、空回答、发布失败、选择器变更、编码问题 | 真实跑满 3 天无人工补数据 |
| **D9** | 缓冲 + 试点协议文档：问题、基线、发布日、判定规则、当前数据 | 一页纸，任何人能照着复现 |
| **D10** | 发布后第一次复盘（3–7 天信号）：继续观察 / 调整内容 / 换渠道 | 不急着下结论；记录调整理由 |

**基线从 D1/D2 开始，D6 发布**，所以基线是 4–5 天；如果 D1 只完成开通没开始采样，发布顺延到 D7。**基线开始后指标口径冻结**，只加展示不改算法。

### D1/D2 的执行方式（代码已就绪，2026-11-25）

两个采集器已经写好并测过（假 HTTP，不花真钱），缺的只是 key：

```bash
# 1. 配 key：复制模板再填，或直接设环境变量（环境变量优先）
cp backend/data/keys.local.example.json backend/data/keys.local.json
#    keys.local.json 已被 .gitignore 排除

# 2. 看采集器状态（会显示「可用 / 未配置」与各自支持的模型）
python backend/scripts/collect.py --list

# 3. 采一条，输出里直接有「搜没搜、引了几条、原始响应在哪」
python backend/scripts/collect.py --question "沈阳哪一家律所最专业" --model deepseek --once
python backend/scripts/collect.py --question "沈阳哪一家律所最专业" --model doubao --once
```

输出形如：

```
✓ 沈阳哪一家律所最专业  deepseek → 812 字  | 已联网搜索×1，3 条引用  | raw=collect://raw/2026-11-25/deepseek-...json
```

三种 0 引用要分开看，处理方式完全不同：

| 输出 | 含义 | 下一步 |
|---|---|---|
| `未触发搜索，0 条引用` | 平台判断不需要搜 | 改问法，或加「请联网查」提示（标注为搜索增强） |
| `已联网搜索×1，0 条引用（搜到了但没被引用）` | 搜了，答案没用任何来源 | 正常现象；说明该问题的答案不靠引用支撑 |
| `平台未报告，N 条引用` | 豆包没给 search 计数 | 以引用为准，不影响判定 |

**成本不写死单价**：`answer.cost` 留空，只记 `token_in/token_out`。官方价目随账号与时段变，
写死一个数字等于给以后埋错账；要算月度成本，用 token 数乘当期价目。

**模型 ID 会变**：豆包的 `doubao-seed-2-1-pro-260915` 带日期版本，平台迭代后下线。
报 `BAD_REQUEST` 时先用 `GEO_DOUBAO_MODEL` 换成你账号里实际开通的模型。

### D3 已就绪：按缺口循环采（2026-11-25）

```bash
# 跑一轮补缺口，然后每小时检查一次；Ctrl+C 停
python backend/scripts/collect.py --model deepseek --loop --interval 3600

# 只想看一轮的账，不进入循环
python backend/scripts/collect.py --model deepseek --once
```

每轮打印一行，出问题时能立刻分清是哪种情况：

```
[12:50:33] 第 1 轮 · 2026-11-25 · doubao：计划缺口 17 → 补采 3，失败 14，今日还差 14
```

**幂等的单位是「槽位」不是「内容」**。每条答案记 `(日期, 第几次)`，同一天同一槽位
只能有一条（015 迁移的唯一索引兜底）。所以：

- 同一天再跑一次 = 第 2 条样本，**不是重复**
- 采满之后缺口为 0，第二轮一条都不采——这才是「同日重跑不产生重复样本」
- 平台逐字返回相同答案时，3 次采样仍然是 3 条（早期按内容哈希判重会吞掉后两条，
  样本数永远够不到计划量）

**超计划拒绝发生在调用之前**：计划 3 次/天，第 4 次直接 `NO_SLOT`，一分钱不花。
人工补采加 `--force`。

**限流会收手**：连续 3 次 `RATE_LIMITED`/`TIMEOUT`/`5xx` 就结束本轮（继续打只会
加重限流）；问题文本写错这类配置错误不中止，其余问题照常采。



**文章不要等 API 全做完再写**：D1 开始采样，D3 就开始写，D5 定稿，D6 发。采样和写作是两条并行线；
等"系统全做好"再写文章，等于把试点往后拖一周。

### 试点文章清单（D3–D5 并行）

只写一篇，围绕目标问题。写之前先确认：这个问题有真实搜索需求，当前品牌 0 提及或竞品有提及；不要选品牌词。

- **标题**：直接复述问题（"沈阳离婚律师收费标准是多少？"），不要品牌口号。
- **开头 100 字**：先给结论/答案，再展开；AI 摘要偏好可抽取的结论。
- **正文**：事实、日期、数字、机构名、可核验来源；H2/H3 分节，一段一个要点。
- **品牌**：自然出现（是谁、做什么、资质/案例），全文 2–3 次，不硬广。
- **信源**：引用平台常引用的来源（知乎/公众号/新闻/百科），不要只引自家官网。
- **渠道**：选一个平台常引用的渠道（知乎/公众号），作者资料/机构认证填完整。
- **长度**：1500–2500 字，配 3–5 条 FAQ。
- **合规**：律师/教育等行业有广告限制，不做"最专业/第一/保证"这类不可证实或违规的表述。

**一篇就够，不要一次写 10 篇**。先证明这一篇能被引用、能拉动提及率，再把写法复制到其他问题。

### 试点对象怎么建

- **新建一个试点 tracker**，不要往演示 tracker 里灌真实答案——否则种子数据和真实数据混在一起，前后对比没有意义。
- 用独立的 question set：目标问题 + 对照问题；采样计划 3 次/天。
- `raw_uri` 统一 `collect://deepseek/...`，和演示数据 `s3://geo-raw/demo/` 一眼可分（roadmap 风险登记第 5 条）。

## 六、风险与 fallback

| 风险 | 信号 | 预案 |
|---|---|---|
| 模型判断不搜索 | 同一问题多次调用，`web_search` 次数为 0、引用为空 | 先用 system prompt 明确要求搜索（标记为「搜索增强模式」），或改用 Search API + 模型的 RAG 管线；**不要把「没搜索」当成「没提及」** |
| 搜了但没引用 | 有 `web_search` 调用，`annotations` 为空 | 正常现象（检索了但没采纳）；记录 `search_called=true, citations=0`，与「没搜索」分开统计 |
| API 引用与产品端不一致 | App 里有引用，API 没有（或反过来） | 以 API 为主做连续采样，每周人工抽 1 次 App 对账；差异写进报告，不混成一套数字 |
| 渠道选择器失效 | 发布卡在选元素/超时 | 换渠道（搜狐已修过）；预算 1 天校准，不硬磕 |
| 样本不足/噪声大 | 14 天样本 < 21，或日间波动 > 30pp | 延长到 30 天；提高每天样本数；不提前下结论 |
| 内容发了但没效果 | 14 天提及率不变 | 先查是否被索引/是否选对信源；迭代一次；仍无变化则换平台或选题 |
| Key/账号延迟 | D1 开不出来 | D1 改为归因 v1（不需要 key），账号并行办；代码不顺延 |

## 七、时间总账

- **试点代码段**：10 个工作日（D1–D10，含 2 天缓冲）≈ 2 个日历周。**这不是项目总长。**
- **观察段**：发布后 14 天出中期、30 天结案；与代码段部分重叠
- **第一个可信结论**：D1 起约 **5 周**
- **规模化**：结论为正后 10 个工作日（AI 加速 5–7 个），总计约 **7–8 周**
- **可选复刻**：再 6–7 个工作日（AI 加速 3–4 个），总计约 **9 周**

**观察期不是空等**：可以在分支上先把机会评分/E3 做出来，但**不要部署到试点实例**——一旦改了采集或指标代码，前后对比就不干净。
试点为正再合并，总计可压到 6–7 周；试点为负，这部分工作可能白做，要自己权衡。

按每天 1 个有效人日算。你若一天能推 2–3 人日，代码段可压到 4–5 天，但 14–30 天的观察期压不了。

## 八、AI 加速版（按 2–3 人日/天推进，5 个工作日跑通代码）

把 D2/D3 合并、D4/D7 合并、不做新看板（复用 `/publish` 与 `/metrics/by-question`），只保留阻断性验证：

| 天 | 合并后的任务 | 判据 |
|---|---|---|
| A1 | 平台对比选定（DeepSeek/豆包各 3 次）+ 开通 + 试点对象 + 1 次真实调用 + 开始 3 次/天采样 | 真实回答入库，`collect://` 前缀；能看到搜索次数与引用 |
| A2 | adapter（含 `citations` 解析入 `citation` 表）+ 调度 + 幂等 + 采集后提及重算 | 同日重跑不重复；提及数与手工核对一致；引用条数与原始响应一致 |
| A3 | 归因 v1（按问题/模型/窗口）+ 复用现有页面 + 备份 | 与手工 SQL 对拍；备份可恢复 |
