# 效果试点计划（2026-11-25）

> 目标不是"页面像参考系统"，是**客户的品牌在 AI 答案里真的变好，而且能证明**。
> 这份计划只覆盖到"第一个可信的效果结论"；复刻、16 渠道、积分都排在它后面。
> 时间口径：1 人日 = 8 小时；按每天 1 个有效人日排。你若一天能推 2–3 人日，代码段可压缩，观察期压不了。
>
> **先看清"10 天"是什么**：下面的 D1–D10 是**试点代码段**（10 个工作日 ≈ 2 个日历周），不是整个项目。
> 完整时间线：第一个效果结论约 **5 周**（2 周代码 + 3–4 周观察）；规模化约 **7–8 周**；加完整复刻约 **9 周**。见第七节。
> 如果按 AI 节奏推进（2–3 人日/天），见第八节：**5 个工作日把采集/归因跑通，第 8 天发文章，第一份结论约 3 周**。

---

## 一、试点定义

**1 个问题 × 1 个平台 × 1 篇文章 × 1 个渠道 × 至少 14 天（最好 30 天）。**

- 平台：DeepSeek（个人实名可开通，flash 错峰约 ¥100/月，研究结论见 `docs/platform-access-research.md`）
- 问题：目标问题 1 个 + 对照问题 1 个（同类、但本次不投放）
- 渠道：知乎 / 公众号 / 搜狐 中选一个已登录、能发文的
- 样本：目标与对照各 3 次/天；发布前至少 5 天基线，发布后观察 14–30 天

### 判定规则（发布前写死，不许事后挑数据）

| 指标 | 通过线 | 说明 |
|---|---|---|
| 主指标：目标问题提及率 | 发布后 14 天比发布前 7 天提升 **≥ 20pp**（基线 0 时约等于 21 条样本里出现 5 条提及），且提及样本 ≥ 3 条 | 样本 ≥ 21 条/窗口；不足标"样本不足" |
| 对照：同期未投放问题 | 变化 **< 10pp** | 排除"大盘都在涨" |
| 次指标：平均位次 / 情感 | 位次改善或进入前 3；情感不为负 | 有位次的样本才算 |
| 引用归因（可选） | 发布文章 URL 在答案引用中出现 ≥ 1 次 | 平台不返回引用时标"不可测"，不硬凑 |

不满足主指标 → 结论写"**未证明**"，不是"失败"；先分析内容/渠道/平台，再决定是否迭代一次。

## 二、10 个工作日（D1–D10）

| 天 | 交付 | 判据 |
|---|---|---|
| **D1** | 开通 DeepSeek（实名/充值/API key）；建试点 tracker + 目标/对照问题 + 采样计划（3 次/天）；跑通 1 次真实调用 | 真实回答入库，`raw_uri=collect://deepseek/...`；确认 API 返回里**有没有引用 URL**；记录延迟与费用 |
| **D2** | 采集 adapter 完成：错误分类（401/429/5xx/超时/空回答）、原始响应落盘、token/cost 记录；CLI `--once` | 四类失败都能归类；一次成功调用字段完整；单测用假 HTTP，不花真钱 |
| **D3** | 调度 + 幂等：进程内循环，幂等键（问题, 模型, 日期, 样本序）；采集后自动跑提及识别 | 同日重跑不产生重复样本；缺口清单归零；提及数与手工核对一致 |
| **D4** | 归因 v1：`/articles/{id}/impact` 按 `question_id` 限定 + 按模型拆 + 7/14/30 天窗口；URL 归一化匹配（若 D1 有引用） | 与手工 SQL 对拍；对照问题不受影响；http/https、尾斜杠、utm 变体测试通过 |
| **D5** | 渠道连接 + 1 篇文章：登录/检测；选择器校准（首跑 `--show`）；文章围绕目标问题写（品牌、事实、来源、小标题） | 渠道 `connected`；草稿在平台后台可见；标题/正文过平台规则 |
| **D6** | 真实发布 + 实验记录：`published_url`、发布时间、目标问题、渠道、基线窗口 | `publication.status=published`；URL 可访问；基线 ≥ 5 天 × 3 次 |
| **D7** | 试点看板（目标 vs 对照、日提及率、样本数、发布日标线）+ 数据库备份/恢复 | 看板与接口一致；恢复后单测全绿 |
| **D8** | 缓冲：处理限流、空回答、发布失败、选择器变更、编码问题 | 真实跑满 3 天无人工补数据 |
| **D9** | 缓冲 + 试点协议文档：问题、基线、发布日、判定规则、当前数据 | 一页纸，任何人能照着复现 |
| **D10** | 发布后第一次复盘（3–7 天信号）：继续观察 / 调整内容 / 换渠道 | 不急着下结论；记录调整理由 |

**基线从 D1/D2 开始，D6 发布**，所以基线是 4–5 天；如果 D1 只完成开通没开始采样，发布顺延到 D7。**基线开始后指标口径冻结**，只加展示不改算法。

### 试点对象怎么建

- **新建一个试点 tracker**，不要往演示 tracker 里灌真实答案——否则种子数据和真实数据混在一起，前后对比没有意义。
- 用独立的 question set：目标问题 + 对照问题；采样计划 3 次/天。
- `raw_uri` 统一 `collect://deepseek/...`，和演示数据 `s3://geo-raw/demo/` 一眼可分（roadmap 风险登记第 5 条）。

## 三、观察期（D+7 / D+14 / D+30）

| 节点 | 动作 | 产出 |
|---|---|---|
| 每天 10 分钟 | 看采集健康：失败率、缺口、空回答；异常才动手 | 不产生新代码 |
| 发布后 7 天 | 第一次看趋势，不判定 | 记录样本量与噪声 |
| 发布后 14 天 | 按判定规则出中期结论 | 中期一页纸 |
| 发布后 30 天 | 结案：目标 vs 对照，写清"证明了什么/没证明什么" | 客户案例或复盘报告 |

**观察期不要改指标口径、不要换模型、不要动采样频率**；要改就等结案后。

## 四、规模化（试点为正才启动，约 10 个工作日）

| 顺序 | 内容 | 人日 | 前置 |
|---|---|---|---:|
| S1 | 机会评分：gap × 竞品提及 × 可发布信源 × 业务价值；按问题/模型出 Top 10；一键建文章 | 2.0 | 试点为正 |
| S2 | 内容工作室六阶段（E3），发布段复用已真实的渠道链路 | 4.0 | S1 |
| S3 | 第二个平台 adapter（豆包或 Kimi）+ 多平台对比 | 1.5–2.0 | 试点为正 |
| S4 | 客户月报模板：本月做了什么、提及率/位次/情感变化、下月建议 | 1.0 | S1–S3 |
| S5 | 备份/最小可观测补齐 | 1.5 | 随时 |

**试点为负怎么办**：不启动规模化。用 2–3 天做一次迭代（换内容形态/换渠道/换问题），再观察 14 天；仍无变化就换平台或换选题，不堆功能。

## 五、明确不做（试点期间）

- E1b/E1c/E1d/E1e（第三栏、复制、双视图、筛选条、抽屉）——演示手感，不产生效果
- E2 16 渠道——一个平台没跑通前，16 个空渠道没有意义
- E4 AI 助手 + 积分——1–2 人使用，积分是装饰
- H4 多用户/租户/PostgreSQL、H5 计费/开放 API——决策 012 已移出范围
- 完整复刻——等试点出结论、且客户明确要看"和参考系统一样"时再排（约 6–7 个工作日）

## 六、风险与 fallback

| 风险 | 信号 | 预案 |
|---|---|---|
| API 不返回引用 URL | D1 调用结果里没有 source/citation | 主指标改为提及率/位次；URL 归因降级为每周人工采网页版一次，不写自动化 |
| 渠道选择器失效 | 发布卡在选元素/超时 | 换渠道（搜狐已修过）；预算 1 天校准，不硬磕 |
| 样本不足/噪声大 | 14 天样本 < 21，或日间波动 > 30pp | 延长到 30 天；提高每天样本数；不提前下结论 |
| 内容发了但没效果 | 14 天提及率不变 | 先查是否被索引/是否选对信源；迭代一次；仍无变化则换平台或选题 |
| Key/账号延迟 | D1 开不出来 | D1 改为归因 v1（不需要 key），账号并行办；代码不顺延 |

## 七、时间总账

- **试点代码段**：10 个工作日（D1–D10，含 2 天缓冲）≈ 2 个日历周。**这不是项目总长。**
- **观察段**：发布后 14 天出中期、30 天结案；与代码段部分重叠
- **第一个可信结论**：D1 起约 **5 周**
- **规模化**：结论为正后 10 个工作日（AI 加速 5–7 个），总计约 **7–8 周**
- **可选复刻**：再 6–7 个工作日（AI 加速 3–4 个），总计约 **9 周**

**观察期不是空等**：可以在分支上先把机会评分/E3 做出来，但**不要部署到试点实例**——一旦改了采集或指标代码，前后对比就不干净。
试点为正再合并，总计可压到 6–7 周；试点为负，这部分工作可能白做，要自己权衡。

按每天 1 个有效人日算。你若一天能推 2–3 人日，代码段可压到 4–5 天，但 14–30 天的观察期压不了。

## 八、AI 加速版（按 2–3 人日/天推进，5 个工作日跑通代码）

把 D2/D3 合并、D4/D7 合并、不做新看板（复用 `/publish` 与 `/metrics/by-question`），只保留阻断性验证：

| 天 | 合并后的任务 | 判据 |
|---|---|---|
| A1 | 开通 DeepSeek + 试点对象 + 1 次真实调用 + 开始 3 次/天采样 | 真实回答入库，`collect://` 前缀 |
| A2 | adapter + 调度 + 幂等 + 采集后提及重算 | 同日重跑不重复；提及数与手工核对一致 |
| A3 | 归因 v1（按问题/模型/窗口）+ 复用现有页面 + 备份 | 与手工 SQL 对拍；备份可恢复 |
| A4 | 渠道登录/校准 + 文章草稿 + 发布预演（不真发） | 渠道 `connected`；草稿在后台可见；预演通过 |
| A5 | 缓冲：只修阻断性 bug + 写试点协议 | 连续 3 天无人工补数据 |

**A6–A8 等基线到 7 天（21 条样本）再真发**；想再快可以把采样提到 5 次/天，5 天就有 25 条，但日间波动看得少。
**14 天结论约第 3 周，30 天结案约第 5 周。**

省下来的是写代码和搭页面的时间，不是验证的时间：采集 / 入库 / 提及 / 发布 / 归因这 5 条链路仍然要过单测 + 一次真实跑通。

## 九、Bug 分级：哪些能后期修，哪些不能

**必须现在对（错了补不回来）**：

- 采样重复/缺失、日期边界（决策 007，按本地自然日）、提及识别
- 发布状态与 `published_url`、原始响应存档（`collect://` 可回溯）
- 归因的分母与窗口口径

**可以后期修（不影响试点结论）**：

- UI 细节、非试点页面、错误文案、性能、边缘配置
- E1b/c/d/e、E2 16 渠道、E4 积分、完整复刻

原则：**数据错了不能事后补，界面丑可以以后改。** 试点期只对上面 5 条链路做完整验证，其余记进 bug 清单，不阻塞发布。
