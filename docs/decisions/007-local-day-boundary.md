# 007 日期按业务时区的自然日，不按 UTC

- 日期：2026-11-24
- 状态：已采纳

## 背景

`collected_at` 存的是带时区的 ISO8601，例如 `2026-11-20T09:00:00+08:00`。
指标查询原先用 SQLite 的 `date(collected_at)` 分组，看起来没问题——种子数据都是 09:00，
转成 UTC 是 01:00，还是同一天。

但实测 `date('2026-11-20T00:30:00+08:00')` 返回 `2026-11-19`：SQLite 会先把带偏移的时间
转成 UTC 再取日期。于是**北京时间 00:00–07:59 采集的样本会被算到前一天**。
做缺口清单时这个问题会直接暴露：缺口按本地日算，看板按 UTC 日算，两边对不上。

## 决策

所有"按天分组"的地方统一用本地日期：

```python
substr(collected_at, 1, 10)
```

封装在 `repositories/sqlutil.py` 的 `day_of()`，10 处查询全部改用它（含 `run_item.attempted_at`）。
存储格式固定带 `+08:00`，所以前 10 位就是北京时间日期；即使某天写入了不带时区的时间，
截取仍然给出本地日期，比 `date()` 更稳。

## 代价

| 代价 | 说明 |
|---|---|
| 依赖"存储格式带偏移"的约定 | 若将来改存 UTC（带 Z），这里要跟着改成 `datetime(..., '+8 hours')` |
| 不能用 SQLite 的日期函数做区间运算 | 区间比较仍可用字符串比较，因为 ISO8601 定长且可字典序比较 |
| 迁移到 PostgreSQL 时要换写法 | `to_char(collected_at AT TIME ZONE 'Asia/Shanghai', 'YYYY-MM-DD')` |

## 替代方案

- **继续用 `date()`**：省事，但凌晨样本会漂到前一天，且与业务直觉不符。
- **存 UTC 并在展示层转换**：更"标准"，但要改全部写入路径与历史数据，收益不抵成本。
- **给每行加一列 `local_date`**：查询最快，但多一列冗余，且写入方必须记得填。等真有性能问题再考虑。

## 补充（2026-11-26）：生成"今天/明天"也要走业务时区

上面锁的是**从存储时间取日期**（`substr`）。漏了一类：代码里**凭空生成**"今天/明天"
的地方原先写 `date.today()`——它取服务器本地时区，本机是 +08 看不出问题，
部署到 UTC 服务器后北京时间 00:00–07:59 会算成前一天。

已收口到 `geo/business_time.py`（固定 +08:00、与采集端 `DEFAULT_TZ` 同偏移、
不依赖系统 tzdata），三处全部改用它：

- FR-012 层级变更生效日（`config_repository.tomorrow()`）；
- 发布前基线锚点回退（`content_service`）；
- 默认查询范围（`api/app.py` 的 `_period()`，16 个接口共用——这是影响面最大的一处，
  报错前用 `date.today()` 会让这些接口在 UTC 服务器的默认范围集体错一天）。

**不改的一处**：`app.py:_now()` 与 `audit_service` 的 `datetime.now().astimezone()`
是"记录事件此刻"，存的是绝对时刻 + 服务器偏移，不是"按天分组"；UTC 机器上存
`+00:00` 仍是正确时刻，不参与决策 007 的日期口径，因此保持原样。

测试用注入 UTC 时刻验证：UTC 时钟是 11-26 16:30 时，业务日期必须是 11-27
（次日 11-28），`date.today()` 在这条判据上必红。`_period()` 另用"冻结服务器日期
与业务日期为不同两天"的方式验证默认范围取业务日期，退回 `date.today()` 精确红。
