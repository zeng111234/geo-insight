# 012 · 范围收敛：只服务 1–2 人内部使用

- 日期：2026-11-25
- 状态：已采纳（当前范围，可随需求变更）
- 影响范围：`docs/roadmap.md` 的 H4/H5、后续排期口径；不改代码
- 关联：008（session 不进表）、006（不用 Alembic）在本范围下继续有效

## 背景

路线图把 H4（多用户、租户隔离、PostgreSQL、备份、可观测、并发写，12–15 人日）和
H5（计费、配额、开放 API、SLA，20+ 人日）列为后续阶段。2026-11-25 明确：
**系统目前只面向 1–2 人内部使用，不是多租户 SaaS，也不对外售卖。**

如果继续按 H0–H5 全量算，会把 34.7 人日的「多人/商业化」当成近期计划，排期失真。

## 决策

1. **H4-1（多用户/角色）、H4-2（租户隔离）、H4-3（PostgreSQL）不做。**
   现有的单租户 + SQLite + 进程内 session 与 1–2 人范围匹配，不再为「以后可能多人」预付复杂度。
2. **H5 整体不做**（计费、配额、开放 API、SLA、自助入驻）。
3. **H4 里只保留「1–2 人也会遇到」的部分**，且不按原估算排期：
   - H4-4 备份与恢复：保留，按 1.0 人日。数据只有一份，丢了就是丢了。
   - H4-5 可观测：只做最小日志与健康页，按 0.5 人日（原 2.0 不做）。
   - H4-6 并发写：先开 WAL + 单写线程；只有采集并发把 P95 拖过 2 秒才升级。
4. **剩余计划按两档算**（写进 roadmap 顶部）：
   - 真用闭环：H2.5 工作台 5.2 + H3 7.0 = **12.2 人日**；
   - 完整复刻：再 + E3 4.0 + E4 4.5 = **20.7 人日**；
   - 可靠性尾巴：再 + 备份 1.0 + 最小可观测 0.5 ≈ **22.2 人日**。

## 边界

- 这不是「永远不做多人」，是「当前不为此付费」。将来真要多人，H4-1/2/3 仍可按原方案启动。
- `tenant_id` 保留在表里、`_tenant(request)` 保留参数化。**不做的是多租户产品化，不是删掉隔离字段**——
  删了以后要加回来，成本比留着高。
- 决策 008 的代价（重启掉线、多进程互不可见）在 1–2 人场景可接受；
  决策 006 的代价（迁移链自己维护）同样可接受。两条都不需要为多人场景提前改。

## 代价与风险

- **2 人变 5 人不是改配置**：session 在进程内、SQLite 单写，扩之前要重新评估。触发信号是「同时在线 > 2」或「采集时 P95 > 2s」。
- **没有开放 API/计费**，外部系统接不进来；客户若要求对接，H5 要重新估算，不能按 20+ 直接套。
- **单进程单库是单点**：备份从「可选」变成「必须」，这也是 H4-4 被保留的原因。
