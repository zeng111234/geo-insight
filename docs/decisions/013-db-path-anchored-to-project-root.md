# 013 · 数据库路径固定跟随项目根，不跟随当前目录

- 日期：2026-11-25
- 状态：已采纳
- 影响范围：`settings.py` 的 `database_path`、`backup-team.bat`、`scripts/doctor.py`

## 背景

用户提出一个硬约束：**这个仓库在两台电脑上轮流跑，程序不能因为路径出问题**。

检查时发现一个已经在发生的故障，不是假设：

| 文件 | 来源 | 状态 |
|---|---|---|
| `backend/geo.db` | 双击 `start.bat`（脚本先 `cd backend`） | 5.0MB，迁移 v10，今天在用 |
| `geo/geo.db` | 命令行在项目根启动 | 4.8MB，11-12 的旧库，**没有 `schema_migration` 表** |

原因是 `database_path` 的默认值是相对路径 `"geo.db"`，于是 "库在哪" 取决于 "从哪个目录启动"。
用户看到的现象是「数据丢了」，实际是打开了另一个文件。

这个缺陷在多机器场景下更严重：换一台电脑、换一种启动方式（双击 vs 命令行 vs 团队脚本），
就可能看到另一份数据，而且没有任何提示。没有 `schema_migration` 的那个库更危险——
它会被当成「旧库」重新认领基线并跑一遍迁移，结构与数据都可能与另一个库分叉。

## 决策

1. **`database_path` 默认值改为 `PROJECT_ROOT / "geo.db"`**，用 `__file__` 推导，与 cwd 无关。
   `GEO_DB_PATH` 环境变量仍然优先（测试靠它指向临时库）。
2. **`backup-team.bat` 跟着改**：从 `cd backend` + 相对 `geo.db` 改成在项目根直接 `copy`。
   不改的话备份会静默失败——它找不到文件只打印一行提示，很容易被忽略。
3. **`doctor.py` 保留「数据库分叉」检查**：路径已修，但老机器上那份 `backend/geo.db`
   不会自己消失，换机器时应当报出来让人决定留哪份。

## 代价

- 已经分叉的机器需要手工合并一次：先确认哪份是最新的，另一份改名归档。
  这台机器上做的是把 v10 的 `backend/geo.db` 移到根目录，旧的改名 `geo.db.archive-2026-11-12`。
  代码改不了这件事，只能靠自检脚本提醒。
- 数据库文件现在固定在一个位置，也就固定了"项目不能随意挪目录"——挪了之后 `PROJECT_ROOT`
  跟着变，库也跟着走。这是期望行为。

## 验证

- `test_settings_paths.py` 4 条：不同 cwd 下路径相同、是绝对路径、落在项目根、`GEO_DB_PATH` 仍可覆盖。
  变异自检：改回相对 `"geo.db"`，红 2 条；还原后全绿。
- 实测双实例：端口 8123（cwd=项目根）与 8124（cwd=backend，模拟 `start.bat`）
  同时运行，`/v1/trackers` 响应**逐字节相同**（1322 字节 / 2 个对象），
  且 `backend/geo.db` 没有被重新创建——证明两种启动方式用的是同一个文件。
- 全量 308 项单测、冒烟、页面契约、浏览器 DOM、分页行为全过。
