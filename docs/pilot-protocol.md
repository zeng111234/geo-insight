# 试点协议（预注册，一页纸）

> 这份文档的目的：**发布前就把怎么判、判什么写死**，防止看到数据之后再挑口径。
> 判定规则的唯一实现是 `content_service.PILOT_RULE`，本文只是它的人类可读版。
> 要改阈值 = 开一次新试点 + 在 `docs/decisions/` 留记录；不许在这份文档上改个数就当改了规则。

---

## 1. 这次试点是什么

**1 个目标问题 × 1 个对照问题 × 1 个平台 × 1 篇文章 × 1 个渠道 × ≥14 天观察。**

三个角色不要混：

| 角色 | 是谁 | 干什么 |
|---|---|---|
| 被测平台 | DeepSeek / 豆包 | 我们**问它**问题，看答案里有没有客户品牌。它是体检仪器，不是发文章的地方 |
| 发布渠道 | 知乎 / 公众号 / 搜狐 | 文章发到这里，再用平台 API 去问，看引用有没有出现这篇文章 |
| 内容 | 人写（可 LLM 辅助） | 围绕目标问题写一篇，1500–2500 字，带 3–5 条 FAQ |

**基线从第一次真实采集开始**，不是从今天。发布前至少 5 天 × 3 次；发布后观察 14 天（最好 30 天）。
基线开始后指标口径冻结，只加展示不改算法。

## 2. 判定规则（发布前写死）

| 项 | 值 | 出处 |
|---|---|---|
| 主指标：目标问题提及率提升 | **≥ +20.0pp** | `PILOT_RULE["target_lift_pp"]` |
| 对照问题同期变化 | **< 10.0pp**（绝对值） | `PILOT_RULE["control_max_pp"]` |
| 每个窗口最少样本 | **≥ 21 条** | `PILOT_RULE["min_window_samples"]` |

窗口：发布日往前 7 天（before）对比发布后 14 天（after）。21 条 = 7 天 × 3 次/天，是"能下结论"的下限。

四种结论，`/pilot` 页直接显示，不需要人工解释：

| status | 条件 | 怎么说 |
|---|---|---|
| `effective` 有效 | 目标 ≥ +20pp 且对照 < 10pp | 可以写客户案例 |
| `inconclusive` 不足 | 涨了但不够，或对照也在动 | 不排除平台整体变化，继续观察 |
| `negative` 无效 | 目标没涨（≤ 0） | 分析内容/渠道，不叫"失败"叫"未证明" |
| `insufficient` 样本不足 | 任一窗口 < 21 条 | 不下结论。**发布前就会拦你** |

**没有对照问题，永远不给"有效"**——目标涨了也可能是整个平台在变。
**全对象口径不判定**——数字混了其他问题，判不出这一篇带来的变化。

发布前系统会算 `baseline`，样本不够就报 `ready=false` 和 `shortfall`。
发布日一旦过去，那段窗口就不会再长出新样本；**发布前样本不足 = 这篇永远判不了**。

## 3. 执行步骤（按顺序，每步都有验收）

### 步骤 1：建试点对象（现在就能做，不需要 key）

```bash
python backend/scripts/setup_pilot.py \
  --name "辽征试点" --brand "辽宁辽征" \
  --target "沈阳离婚律师收费标准是多少" \
  --control "沈阳合同纠纷律师怎么找" \
  --model doubao --keywords "离婚,律师收费"
```

先看不写：`--dry-run`。脚本一次做完四件事：独立 tracker、导入目标+对照问题（都标 core）、
把 `active_question_set_id` 指到新集、写 `sampling_plan`（3 次/天）。最后自己算一遍缺口，
算不出来就整笔回滚。**同名对象会拒绝**，防止建出两个试点让基线分叉。

验收：输出里有"今日计划 6 条，当前缺口 6 条"（2 问题 × 3 次）。

> 为什么不用页面建：`/settings` 的采样计划区是只读的，全站没有写入接口。
> 手工改库不可复现，所以做成脚本。

### 步骤 2：配 key（卡在这里，需要你提供）

```bash
cp backend/data/keys.local.example.json backend/data/keys.local.json
# 填入 {"deepseek": "sk-...", "doubao": "..."}，该文件已被 gitignore
python backend/scripts/collect.py --list    # 两个采集器应显示"可用"
```

没有 key 也能跑离线演练（`GEO_COLLECTOR_CSV`），但**离线数据不能算基线**——基线必须是真平台回答。

### 步骤 3：采基线（≥5 天，每天自动）

```bash
python backend/scripts/collect.py --tracker <步骤1的id> --model doubao --loop --interval 3600
```

每轮打印缺口、补采、失败。超计划直接 `NO_SLOT` 不花钱；连续 3 次限流/超时会收手。
**幂等单位是槽位（日期 + 第几次）不是内容**：平台逐字返回同样答案，3 次仍是 3 条样本。

验收：`/monitor` → 采集健康，缺口归零；`/v1/trackers/{id}/sampling-plan` 显示计划。

### 步骤 4：写文章（与步骤 3 并行，别等采样跑完）

标题直接复述目标问题；开头 100 字给结论；正文有事实、日期、数字、可核验来源；
品牌自然出现 2–3 次；信源别只引自家官网；1500–2500 字 + 3–5 条 FAQ。
律师/教育行业不做"最专业/第一/保证"这类不可证实的表述。

### 步骤 5：发布（基线够了才能发）

发之前看文章详情的 `baseline` 字段：`ready=false` 就别发，先补采样。
在 `/publish` 页选渠道发布，记下 `published_url` 和发布时间。

验收：`publication.status=published`，URL 能打开。

### 步骤 6：等 14 天，看结论

打开 `/pilot` 页：目标 vs 对照、日提及率、样本数、发布日标线、引用证据、一句话判定全在一页。
接口是 `GET /v1/articles/{id}/impact?windowDays=14&scope=question`。

**scope 必须是 `question`**，全对象口径不判定。发布后 7 天只看趋势不下结论，14 天出中期结论。

## 4. 三条底线

1. **不许事后调阈值**：看到数据再说"其实 15pp 也算涨"等于没做试点。要改就开新试点 + 写决策。
2. **不许混数据**：试点用独立 tracker，`raw_uri` 走 `collect://`，和演示数据 `s3://geo-raw/demo/` 一眼可分。
3. **不许造数**：没触发搜索、搜了没引用、平台未报告是三种不同状态，分别记，不能都填 0。
   `answer.cost` 只留 token 数按当期价目算，不写死单价。
