# GEO Insight 长期计划

> 状态：2026-11-24 制定。`specs/001-geo-insight-platform/tasks.md` 是首版实现清单，本文件是**后续演进的唯一依据**。
> 工作量单位为「人日」，一个人投入 4 小时算半人日；不给日历日期，因为日历受投入强度影响，承诺日期只会变成谎言。

## 七、每个阶段都适用的硬约束

1. **回归闸门**：改动后必须过 438 项（单测 178 / 冒烟 86 / 页面契约 77 / 浏览器 75 / 分页 22），黄金窗口 22.22%、9 样本、-23.3pp 等 19 项手算值不许动。测试数只增不减，减少必须写明原因。
2. **结构变更只走迁移**：已应用的迁移文件不许改（checksum 会拦），改结构就新增版本号。
3. **关键断言必须变异自检**：故意改错实现，确认检查会变红；红不了说明这条断言没在验证任何东西。
4. **诚实标注验证层级**：只到「能跑通」就写「行为未验证」，不用「应该可以了」收尾。
5. **新增限制要同步 README**：做了半截的能力，写进「尚未实现」，不靠口头记忆。
6. **日期一律按本地自然日**：按天分组用 `sqlutil.day_of()`，不要用 SQLite 的 `date()`——它会把带偏移的时间转成 UTC，北京时间 00:00–07:59 的样本会漂到前一天（决策 007）。

**同步团队 11 个提交时暴露的两个真问题**（都是合并之后才浮现的，不是新写的 bug）：

1. 团队的 CSRF 中间件挡住了新 DELETE 接口（403 CSRF_REJECTED）。这是中间件该做的事，
   改的是测试不是中间件。另加一条断言「没有 token 的删除被 403 且一行不动」——
   守的不是「中间件存在」（那是 003 的测试），而是「这个新接口确实被中间件覆盖到」。
2. 迁移 010 给 `tracker` 加了 `active_question_set_id REFERENCES question_set(id)`，
   删问题集时撞外键。重排删除顺序：先把 tracker 上的指针置 NULL 再删 question_set。
   顺带发现原顺序里 `question` 排在 `article` 之前，而 `article` 引用 `question`——
   测试没造文章所以没暴露。**级联删除的顺序缺陷，只有造了全量数据的测试才能发现。**

验证：单测 301 项（合并前 300，新增 1 条 CSRF 断言）、冒烟、页面契约、浏览器、分页全过；
CDP 真实点击 9 项（按钮顺序 / 弹框 / 禁用态 / 错名称拒绝 / 正确名称放行 / 取消不删 /
暂停生效 / 恢复生效 / 全程无 JS 异常）。
